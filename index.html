Engineering principles

Six rules I build by. Each one comes from something that broke, or nearly did, in a pipeline of mine.

  • Quarantine, never delete

    Every source row ends up in Silver, in quarantine with a reason, or as a counted duplicate. Each job has to prove that rows in equals rows out plus rejected plus duplicates.

    Meridian Freight, Silver layer

  • Move the watermark last

    A watermark advances only after the job’s books balance. I simulated a crash between the write and the watermark; the re-run recovered with no manual repair.

    Meridian Freight, incremental loads

  • Define a KPI once

    Percentages are measures in the semantic model, not stored columns. When Ops, Finance and Sales each compute “on-time” differently, the fix is one documented definition.

    Meridian Freight, 16 documented KPIs

  • Break it on purpose

    I renamed a source column to see what failed. Nothing did: the pipeline stayed green while writing nulls, because accepted_values ignores nulls unless paired with not_null.

    Retail Medallion, incident log

  • Daily can be the right answer

    Buying, staffing and stock decisions were made at day level, so I chose scheduled daily batch over near-real-time. Validation ran before every refresh.

    JKSR Trading, reporting platform

  • Publish the limitations

    My READMEs list what the build is not: which parts ran on one machine, which data is synthetic, which tolerance is a placeholder. A reader should not have to find that out in an interview.

    Every public repo
